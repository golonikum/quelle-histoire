## Модульное и интеграционное тестирование фронт-энда

### Основы автоматизированного тестирования

#### Базовые принципы

- Тот факт, что ваше ПО работает, не может быть доказан: вы можете доказать лишь наличие дефектов. Тесты показывают отсутствие определенных ошибок, но не гарантируют, что ошибок нет совсем. Тесты обычно ищут дефекты, которые встречались прежде, или отслеживают определенного рода ситуации, в которых код должен работать.
- Автоматизированные тесты сокращают задержку между написанием кода и получением обратной связи, делая тем самым процесс разработки более упорядоченным и избавляя от многих сюрпризов.
- Когда тесты автоматизированы, переписывание кода происходит реже, а взаимодействие становится более эффективным. Разработчики могут самостоятельно проверить корректность чужого кода и гарантировать, что они не нарушили работу других участков приложения.
- Хорошо написанные тесты - это лучшая документация, которая только может быть у разработчика. Они всегда должны быть актуальными, служат демонстрацией использования API и помогают другим людям понять, как работает кодовая база.

#### Пирамида (трофей) тестирования

Много полезной информации, в том числе о пирамиде (трофее) тестирования можно найти на следующем ресурсе: [Эффективное тестирование верстки](https://savepearlharbor.com/?p=308941).

Главный вывод:

> Исскуство написания тестов заключается в том, чтобы **правильно скомбинировать разные виды тестирования** для нанесения **максимальной пользы** проекту.

Или, еще проще:

> В реальности вам нужно оценивать, какие тесты на вашу систему дают **наибольший профит при наименьших затратах**.

### Используемые библиотеки

Тестирование производится с помощью библиотеки [Jest](https://jestjs.io/docs/27.x/getting-started). Дополнительно используются библиотеки:

- [React Testing Library](https://testing-library.com/docs/react-testing-library/intro/) (позволяет тестировать компоненты React)
- [React Hooks Testing Library](https://react-hooks-testing-library.com/) (для тестированя React hooks)
- [Axios Mock Adapter](https://www.npmjs.com/package/axios-mock-adapter) (для макетирования запросов)
- [@testing-library/jest-dom](https://testing-library.com/docs/ecosystem-jest-dom/) (сопутствующая библиотека, которая предоставляет удобные средства сопоставления элементов DOM для Jest, например `toHaveClass`, `toBeInTheDocument`, `toHaveTextContent` и др.)
- [@testing-library/user-event](https://testing-library.com/docs/user-event/intro) (`user-event` пытается имитировать реальные события, которые происходят в браузере, когда пользователь взаимодействует с ним)
- [eslint-plugin-testing-library](https://github.com/testing-library/eslint-plugin-testing-library) и [eslint-plugin-jest-dom](https://github.com/testing-library/eslint-plugin-jest-dom) (плагины ESLint для библиотеки тестирования, которые помогают следовать передовым методам и предвидеть распространенные ошибки при написании тестов)

### Покрытие кода

Для подсчета покрытия при запуске тестов нужно передать флаг `--collect-coverage` (или `--collectCoverage`):

```
yarn test-lib --collect-coverage
yarn test --collect-coverage
```

Статистика покрытия записывается в директорию `coverage/{PROJECT_NAME}`.

Вместо того чтобы использовать покрытие кода в качестве самостоятельного показателя, с его помощью можно понять, какие участки программы не покрыты тестами, и следить за тем, чтобы команда двигалась в сторону большего, а не меньшего покрытия.

### Поиск DOM-элементов

- Использовать `getBy...` как можно больше.
- Использовать `queryBy...` только при проверке на несуществование.
- Использовать `await findBy...` только тогда, когда ожидается, что элемент появится после изменения в DOM, которое может произойти не сразу.

Чтобы убедиться, что [тесты соответствуют тому, как пользователи взаимодействуют с нашим кодом](https://testing-library.com/docs/guiding-principles/), рекомендуется следующий приоритет для запросов:

1. `getByRole` - Это должен быть выбор практически для всего. В качестве приятного бонуса с этим селектором мы обеспечиваем доступность нашего приложения. Скорее всего, он будет использоваться вместе с опцией имени `getByRole('button', {name: /save/i})`. Имя обычно является меткой элемента формы, текстовым содержимым кнопки или значением атрибута `aria-label`. Если вы не уверены, используйте функцию [logRoles](https://testing-library.com/docs/dom-testing-library/api-accessibility/#logroles) или обратитесь к [списку доступных ролей](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/ARIA_Techniques) или к [правилам использования атрибута ARIA элементами HTML](https://www.w3.org/TR/html-aria/#docconformance).
2. `getByLabelText` и `getByPlaceholderText` - Пользователи находят элементы формы по тексту метки, поэтому этот вариант предпочтительнее при тестировании форм.
3. `getByText` - Помимо форм текстовое содержимое является основным способом поиска элементов пользователями. Этот метод можно использовать для поиска неинтерактивных элементов (таких как `div`, `span` и т.д.).
4. `getByTestId` - Поскольку это не отражает того, как пользователи взаимодействуют с приложением, это рекомендуется только в тех случаях, когда вы не можете использовать какой-либо другой селектор.

Если вы все еще не можете решить, какой запрос использовать, проверьте [testing-playground](https://testing-playground.com/) вместе с [screen.logTestingPlaygroundURL()](https://testing-library.com/docs/queries/about/#screenlogtestingplaygroundurl) и их [расширением для браузера](https://chrome.google.com/webstore/detail/testing-playground/hejbmebodbijjdhflfknehhcgaklhano).

Не забывайте, что всегда можно вызвать [screen.debug()](https://testing-library.com/docs/queries/about/#screendebug) в любом месте вашего теста, чтобы увидеть текущий DOM.

Про типичные ошибки при использовании _React Testing Library_ можно почитать в статье [Common mistakes with React Testing Library](https://kentcdodds.com/blog/common-mistakes-with-react-testing-library).

### Тестовые дублеры

**Макеты**, **заглушки** и **шпионы** - это объекты, которые используются для изменения и замены частей приложения, чтобы упростить или сделать возможным его тестирование. Все вместе они относятся к категории **тестовых дублеров** (_test doubles_).

#### Шпионы

Шпионы (_spies_) записывают данные, имеющие отношение к использованию функции, не вмешиваясь в ее реализацию.

В Jest шпионов можно создать с помощью функции `jest.spyOn`. `jest.spyOn(object, methodName)` создает mock-функцию, подобно `jest.fn()`, но еще и отслеживает вызовы к `object[methodName]`. Пример:

```ts
const logger = require("./logger");
const { addToInventory } = require("./inventoryController");

test("logging new items", () => {
  jest.spyOn(logger, "logInfo");
  addToInventory("cake", 2);
  const firstCallArgs = logger.logInfo.mock.calls[0];
  const [firstArg] = firstCallArgs;
  expect(firstArg).toEqual("item added to the inventory");
});
```

#### Заглушки

Заглушки (_stubs_) записывают данные, связанные с использованием функции, и изменяют ее поведение за счет предоставления альтернативной реализации или возвращаемого значения.

Чтобы избавиться от лишнего вывода, нужно вместо функции `logger.logInfo` подставить ее фиктивную реализацию. Для этого нужно из шпиона вызвать метод `mockImplementation` и передать ему фиктивную функцию, созданную с помощью `jest.fn`. Пример:

```ts
const logger = require("./logger");
const { addToInventory } = require("./inventoryController");

beforeAll(() => {
  jest.spyOn(logger, "logInfo").mockImplementation(jest.fn());
});

afterEach(() => {
  logger.logInfo.mockClear();
});

test("logging new items", () => {
  addToInventory("cake", 2);
  const firstCallArgs = logger.logInfo.mock.calls[0];
  const [firstArg] = firstCallArgs;
  expect(firstArg).toEqual("item added to the inventory");
});
```

Функция `jest.mock` позволяет определить, что должно возвращаться при импорте модулей. Таким образом можно создать заглушку на весь модуль, или только на часть его реализации:

```ts
// ...
jest.mock("./logger", () => {
  const originalLogger = jest.requireActual("./logger");
  const partiallyMockedLogger = { logInfo: jest.fn() };
  return { ...originalLogger, ...partiallyMockedLogger };
});
// ...
```

Если в одной директории с модулем создать и директорию с именем `__mocks__`, то после вызова функции `jest.mock`, все операции импорта этого модуля будут ссылаться на одноименный файл внутри `__mocks__`.

#### Макеты

Макеты (_mocks_) изменяют поведение функции, но вместо того, чтобы просто записывать информацию о ее использовании, имеют заранее запрограммированные ожидания.

Как ни странно, если придерживаться наиболее устоявшегося определения макета, это единственный вид тестовых дублеров, который не включен в Jest.

### Примеры тестов

#### Тестирование функций

Самый простой базовый случай, когда нужно убедиться в правильной работе чистой функции (_pure function_). Рассмотрим функцию `sum` (файл `sum.ts`):

```ts
export function sum(a: number = 0, b: number = 0) {
  return a + b;
}
```

Для этого, рядом с файлом `sum.ts` создадим файл `sum.test.ts`:

```ts
import { sum } from "./sum";

describe("function sum", () => {
  test("without args", () => {
    expect(sum()).toBe(0);
    expect(sum(1)).toBe(1);
  });

  test("normal values", () => {
    expect(sum(0, 0)).toBe(0);
    expect(sum(2, 4)).toBe(6);
  });

  test("overhead values", () => {
    expect(sum(Number.MAX_VALUE, Number.MAX_VALUE)).toBe(Infinity);
  });
});
```

В идеале, все чистые функции в проекте (утилитарные функции, валидаторы полей, мапперы-конверторы и т.д.) должны быть покрыты тестами.

#### Тестирование компонентов

Пример тестирования компонента `AttachmentItem` из `dds-ui` с помощью `React Testing Library`:

```ts
import React from "react";
import { cleanup, render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

import { AttachmentItem } from "./AttachmentItem";

describe("component AttachmentItem", () => {
  afterEach(cleanup);

  test("render component", () => {
    render(
      <AttachmentItem description="Description 123" fileSize={25 * 1024 * 1024} filename="FILENAME_123" uuid="123" />,
    );
    expect(screen.getByText(/description 123/i)).toBeInTheDocument();
    const element = screen.getByText(/filename_123/i);
    expect(element).toHaveTextContent("25.00 Мб");
    expect(screen.queryByRole("button")).not.toBeInTheDocument();
  });

  test("delete file action", () => {
    const deleteFile = jest.fn();
    const user = userEvent.setup();

    render(<AttachmentItem description="DESC" fileSize={0} filename="NAME" uuid="123" deleteFile={deleteFile} />);

    await user.click(screen.getByRole("button"));
    expect(deleteFile.mock.calls.length).toEqual(1);
  });
});
```

#### Тестирование хуков

Для тестирования react hooks можно использовать библиотеку `React Hooks Testing Library`. Например, рассмотрим хук `useCounter`:

```ts
import { useState, useCallback } from "react";

export function useCounter() {
  const [count, setCount] = useState(0);
  const increment = useCallback(() => setCount((x) => x + 1), []);
  return { count, increment };
}
```

На примере этого хука можно рассмотреть пару тестов:

```ts
import { renderHook } from "@testing-library/react-hooks";
import { useCounter } from "./useCounter";

describe("hook useCounter", () => {
  test("should use counter", () => {
    const { result } = renderHook(() => useCounter());

    expect(result.current.count).toBe(0);
    expect(typeof result.current.increment).toBe("function");
  });

  test("should increment counter", () => {
    const { result } = renderHook(() => useCounter());

    act(() => {
      result.current.increment();
    });

    expect(result.current.count).toBe(1);
  });
});
```

#### Тестирование mobX сторы

Большинство запросов в наших проектах осуществляется через `axios`, поэтому запросы можно "мокать" с помощью `Axios Mock Adapter`. Рассмотрим тест mobX сторы `User` из проекта `citizen-ui`:

```ts
import axios from "axios";
import MockAdapter from "axios-mock-adapter";

import User from "./User";

describe("store User", () => {
  let mock: MockAdapter;

  beforeAll(() => {
    mock = new MockAdapter(axios);
  });

  afterEach(() => {
    mock.reset();
  });

  test("should load current user", async () => {
    const userStore = new User();

    mock.onGet(`/users/current`).reply(200, {
      id: "1",
      name: "NAME",
      contactDetails: {
        contacts: [
          { type: { kind: "PHONE" }, value: "12345" },
          { type: { kind: "EMAIL" }, value: "email@some.com" },
        ],
      },
    });

    await userStore.loadCurrentUser();

    expect(mock.history.get[0]?.url).toEqual(`/users/current`);
    expect(userStore.info.name).toEqual("NAME");
    expect(userStore.info.phone).toEqual("12345");
    expect(userStore.info.email).toEqual("email@some.com");
  });
});
```

#### Интеграционный тест компонента (с redux и react-router)

В данном примере приходится ставить заглушки не только для запросов, но и для `react-router`.

```ts
import React from "react";
import { Provider } from "react-redux";
import { render, screen } from "@testing-library/react";
import axios from "axios";
import MockAdapter from "axios-mock-adapter";
import { Router } from "react-router-dom";
import ReactRouter from "react-router";
import { createMemoryHistory } from "history";

import { MOCK_CREWMANS as crewmans, MOCK_ORGANIZATION_VIEWS as orgs } from "@coreclass/ecor-ui-lib/src/mockData";

import store from "../../reduxes/store/store";
import { Forces } from "./Forces";

jest.mock("react-router", () => ({
  ...jest.requireActual("react-router"),
  useParams: jest.fn(),
}));

describe("Forces integration tests", () => {
  let mock: MockAdapter;

  beforeAll(() => {
    mock = new MockAdapter(axios);
    global.AutoSizerTestEnv.before();
  });
  afterEach(() => {
    mock.reset();
  });
  afterAll(() => {
    global.AutoSizerTestEnv.after();
  });

  test("should load organizations and crewmans (path: /forces/1/crewman)", async () => {
    jest.spyOn(ReactRouter, "useParams").mockReturnValue({ id: "1", activeTab: "crewman" });
    const history = createMemoryHistory({ initialEntries: ["/forces/1/crewman"] });

    mock.onPost("/api-aggregator/api/extensions/forces/organizations").reply(200, {
      content: orgs,
      totalElements: orgs.length,
      totalPages: 1,
    });
    mock.onPost("/forces/api/process/forces/crewman/filter").reply(200, {
      content: crewmans,
      totalElements: crewmans.length,
      totalPages: 1,
    });

    render(
      <Router history={history}>
        <Provider store={store}>
          <Forces />
        </Provider>
      </Router>,
    );

    const cards = await screen.findAllByRole("card");
    expect(cards.length).toEqual(orgs.length + crewmans.length);

    expect(mock.history.post.length).toEqual(2);

    const crewman = await screen.findByText(crewmans[0].partner?.fullName!);
    expect(crewman).toBeInTheDocument();
  });
});
```
