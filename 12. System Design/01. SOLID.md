# SOLID

SOLID — 5 принципов объектно-ориентированного программирования для создания масштабируемого, поддерживаемого кода (Роберт Мартин, "Дядя Боб").

## 1. Single Responsibility Principle (SRP)

> Каждый модуль, хук или компонент должен отвечать ровно за одну задачу или иметь одну причину для изменения.

Модуль должен отвечать за одного и только за одного актора. Актор - человек или группа людей, которые имеют общие интересы.

### Пример 1.1: Разделение бизнес-логики и представления (Контейнер / Презентер через Custom Hook)

**Антипаттерн**: Компонент одновременно фетчит данные, форматирует валюту, обрабатывает ошибки и рендерит сложный UI.

```tsx
// ❌ Нарушение SRP
export const UserBilling = ({ userId }: { userId: string }) => {
  const [data, setData] = useState<BillingData | null>(null);
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    fetch(`/api/billing/${userId}`)
      .then((res) => res.json())
      .then((res) => {
        setData(res);
        setIsLoading(false);
      });
  }, [userId]);

  if (isLoading) return <div>Загрузка...</div>;
  if (!data) return <div>Ошибка</div>;

  const formattedTotal = new Intl.NumberFormat("ru-RU", {
    style: "currency",
    currency: "RUB",
  }).format(data.amount);

  return (
    <section>
      <h2>Биллинг: {data.userName}</h2>
      <span>Сумма: {formattedTotal}</span>
    </section>
  );
};
```

Решение по SRP:

```tsx
// 1. Ответственность за получение данных
export const useUserBilling = (userId: string) => {
  return useQuery({
    queryKey: ["billing", userId],
    queryFn: () => fetchBilling(userId),
  });
};

// 2. Чистая функция форматирования
export const formatCurrency = (amount: number, currency = "RUB") =>
  new Intl.NumberFormat("ru-RU", { style: "currency", currency }).format(
    amount,
  );

// 3. Презентационный компонент отвечает только за рендер
export const UserBilling = ({ userId }: { userId: string }) => {
  const { data, isLoading, isError } = useUserBilling(userId);

  if (isLoading) return <BillingSkeleton />;
  if (isError || !data) return <BillingError />;

  return (
    <section>
      <h2>Биллинг: {data.userName}</h2>
      <span>Сумма: {formatCurrency(data.amount)}</span>
    </section>
  );
};
```

### Пример 1.2: Атомарные хуки сайд-эффектов (Window Resize + Analytics)

**Антипаттерн**: Хук `useHeaderLogic`, который одновременно слушает скролл окна, ресайз и отправляет событие в Google Analytics.

Решение:

```tsx
// ✅ Отдельные изолированные хуки с одной зоной ответственности
export const useWindowSize = () => {
  const [size, setSize] = useState({
    width: window.innerWidth,
    height: window.innerHeight,
  });
  useEffect(() => {
    const onResize = () =>
      setSize({ width: window.innerWidth, height: window.innerHeight });
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);
  return size;
};

export const useAnalyticsTrack = (
  event: string,
  payload: Record<string, unknown>,
) => {
  useEffect(() => {
    analyticsService.track(event, payload);
  }, [event, payload]);
};
```

## 2. Open-Closed Principle (OCP)

> Программные сущности должны быть открыты для расширения, но закрыты для модификации.

В React `OCP` реализуется через композицию (`children`), `Render Props` и `Compound Components`.

### Пример 2.1: Полиморфные списки и рендер-пропсы

**Антипаттерн**: Внутрь `CardList` каждый раз добавляют новые ветки `if/switch`, когда появляется новый тип карточки (продукт, баннер, промо-пост).

```tsx
// ❌ Нарушение OCP: при добавлении типа 'promo' нужно менять исходный код CardList
export const CardList = ({
  items,
  type,
}: {
  items: Item[];
  type: "product" | "user";
}) => (
  <div className="grid">
    {items.map((item) => (
      <div key={item.id}>
        {type === "product" && <ProductCard data={item} />}
        {type === "user" && <UserCard data={item} />}
      </div>
    ))}
  </div>
);
```

Решение по OCP:

```tsx
// ✅ Открыт для любых карточек через render-функцию, сам компонент не модифицируется
interface GenericListProps<T> {
  items: T[];
  renderItem: (item: T, index: number) => React.ReactNode;
  keyExtractor: (item: T) => string | number;
}

export function GenericList<T>({
  items,
  renderItem,
  keyExtractor,
}: GenericListProps<T>) {
  return (
    <div className="grid">
      {items.map((item, index) => (
        <div key={keyExtractor(item)}>{renderItem(item, index)}</div>
      ))}
    </div>
  );
}

// Использование без изменения GenericList:
<GenericList
  items={promoItems}
  keyExtractor={(i) => i.id}
  renderItem={(item) => <PromoBanner data={item} />}
/>;
```

### Пример 2.2: Compound Components (Паттерн аккордеона/селекта)

```tsx
// ✅ Добавление иконки или тултипа внутрь Header не требует модификации Accordion
export const Accordion = ({ children }: { children: React.ReactNode }) => {
  const [openId, setOpenId] = useState<string | null>(null);
  return (
    <AccordionContext.Provider value={{ openId, setOpenId }}>
      {children}
    </AccordionContext.Provider>
  );
};

export const AccordionItem = ({
  id,
  children,
}: {
  id: string;
  children: React.ReactNode;
}) => <div className="border">{children}</div>;

export const AccordionTrigger = ({
  id,
  children,
}: {
  id: string;
  children: React.ReactNode;
}) => {
  const { setOpenId } = useContext(AccordionContext);
  return <button onClick={() => setOpenId(id)}>{children}</button>;
};

// Расширяем структуру без правок внутренних алгоритмов Accordion:
<Accordion>
  <AccordionItem id="1">
    <AccordionTrigger id="1">
      <CustomIcon /> <span>Заголовок с бейджем</span> <Badge count={5} />
    </AccordionTrigger>
    <AccordionContent id="1">Тело блока</AccordionContent>
  </AccordionItem>
</Accordion>;
```

## 3. Liskov Substitution Principle (LSP)

> Объекты/компоненты подтипов должны корректно заменять базовые сущности без нарушения ожидаемого поведения программы.

В React это означает: компоненты-обертки должны сохранять контракт базового элемента (пропсы HTML-элементов, `ref`, события).

### Пример 3.1: Корректное расширение нативных HTML-элементов

**Антипаттерн**: Кастомный `SearchInput`, который ломает нативные свойства (`onChange`, `disabled`, `ref`), принимая вместо них кастомный `onCustomChange`.

```tsx
// ❌ Нарушение LSP: нельзя подставить вместо стандартного <input />
export const SearchInput = ({
  onCustomChange,
  val,
}: {
  onCustomChange: (t: string) => void;
  val: string;
}) => <input value={val} onChange={(e) => onCustomChange(e.target.value)} />;
```

Решение по LSP:

```tsx
// ✅ Соблюдение контракта: компонент принимает ВСЕ валидные пропсы input + forwardRef
export interface SearchInputProps extends React.ComponentPropsWithRef<"input"> {
  searchIconPosition?: "left" | "right";
}

export const SearchInput = forwardRef<HTMLInputElement, SearchInputProps>(
  ({ searchIconPosition = "left", className, ...restProps }, ref) => {
    return (
      <div className="input-wrapper">
        {searchIconPosition === "left" && <IconSearch />}
        <input
          ref={ref}
          className={clsx("base-input", className)}
          {...restProps}
        />
      </div>
    );
  },
);
SearchInput.displayName = "SearchInput";
```

### Пример 3.2: Взаимозаменяемые провайдеры кэша / стейта

Если у вас есть абстракция над хранилищем (например, `StorageAdapter`), любая реализация (`Local Storage`, `Session Storage`, `IndexedDB`) должна возвращать совместимый интерфейс:

```tsx
export interface KeyValueStore {
  getItem: (key: string) => string | null;
  setItem: (key: string, value: string) => void;
}

export const LocalStoreAdapter: KeyValueStore = {
  getItem: (k) => localStorage.getItem(k),
  setItem: (k, v) => localStorage.setItem(k, v),
};

export const MemoryStoreAdapter: KeyValueStore = (() => {
  const map = new Map<string, string>();
  return {
    getItem: (k) => map.get(k) ?? null,
    setItem: (k, v) => map.set(k, v),
  };
})();

// Хук работает с ЛЮБЫМ адаптером без изменения логики
export const usePersistedState = (key: string, adapter: KeyValueStore) => {
  const [val, setVal] = useState(() => adapter.getItem(key));
  // ...
};
```

## 4. Interface Segregation Principle (ISP)

> Клиенты не должны зависеть от интерфейсов и данных, которые они не используют.

В React: не передавайте весь гигантский объект сущности (`User`, `Product`, `Order`) в компонент, которому нужны 1–2 поля.

### Пример 4.1: Props Segregation в UI-компонентах

**Антипаттерн**: Передача 50-польной модели `User` в аватарку.

```tsx
// ❌ Нарушение ISP: аватарке нужен только url и имя, но она жестко связана со всей схемой User
export const UserAvatar = ({ user }: { user: FullUserModel }) => (
  <img src={user.profile.avatarUrl} alt={user.personalInfo.fullName} />
);
```

Решение по ISP:

```tsx
// ✅ Минимальный независимый интерфейс
interface AvatarProps {
  src?: string;
  alt: string;
  size?: 'sm' | 'md' | 'lg';
}

export const Avatar = ({ src, alt, size = 'md' }: AvatarProps) => (
  <img src={src || '/default.png'} alt={alt} className={`avatar-${size}`} />
);

// Теперь Avatar можно переиспользовать для User, Group, Bot, Product:
<Avatar src={user.avatarUrl} alt={user.name} />
<Avatar src={group.logo} alt={group.title} />
```

### Пример 4.2: Разделение интерфейсов Context

**Антипаттерн**: Единый контекст `AppContext`, в котором лежат тема оформления, сессия пользователя, корзина и методы роутинга. Изменение корзины триггерит ререндер компонентов, слушающих только тему.

```tsx
// ✅ Разделенные изолированные контексты
export const ThemeContext = createContext<{
  theme: "dark" | "light";
  toggleTheme: () => void;
} | null>(null);
export const UserSessionContext = createContext<{
  user: User | null;
  logout: () => void;
} | null>(null);

// Компонент подписывается строго на то, что ему нужно:
export const ThemeToggle = () => {
  const { theme, toggleTheme } = useTheme(); // Никак не реагирует на изменение user / session
  return <button onClick={toggleTheme}>{theme}</button>;
};
```

## 5. Dependency Inversion Principle (DIP)

> Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба типа модулей должны зависеть от абстракций.

В React `DIP` реализуется через `React Context`, передачу зависимостей через параметры хуков / пропсы и `Service Locator` / `DI`.

### Пример 5.1: Инверсия механизма API-запросов через Context

**Антипаттерн**: Компонент напрямую импортирует экземпляр `axios` с жестко зашитым URL.

```tsx
// ❌ Жесткая связь с конкретным клиентом
import { globalAxiosInstance } from "@/services/axios";

export const UserProfile = ({ id }: { id: string }) => {
  useEffect(() => {
    globalAxiosInstance.get(`/users/${id}`); // Невозможно протестировать без мока глобального модуля
  }, [id]);
};
```

Решение по DIP:

```tsx
// 1. Абстракция (контракт)
export interface IUserService {
  getUser(id: string): Promise<User>;
}

// 2. Контекст как контейнер внедрения зависимостей
const ServiceContext = createContext<{ userService: IUserService } | null>(
  null,
);

export const useUserService = () => {
  const ctx = useContext(ServiceContext);
  if (!ctx) throw new Error("ServiceContext missing");
  return ctx.userService;
};

// 3. Компонент зависит от абстракции:
export const UserProfile = ({ id }: { id: string }) => {
  const userService = useUserService();
  const { data } = useQuery({
    queryKey: ["user", id],
    queryFn: () => userService.getUser(id),
  });
  return <div>{data?.name}</div>;
};

// В проде провайдим REST/Axios, в тестах/Storybook — InMemoryMockService:
<ServiceContext.Provider value={{ userService: new MockUserService() }}>
  <UserProfile id="1" />
</ServiceContext.Provider>;
```

### Пример 5.2: Инверсия стратегии валидации формы

```tsx
// Хук формы не знает, какая библиотека проверяет поля (Zod, Yup, чистый regex)
export type ValidatorFn<T> = (values: T) => Record<keyof T, string | undefined>;

export function useCustomForm<T extends Record<string, unknown>>(
  initial: T,
  validate: ValidatorFn<T>,
) {
  const [values, setValues] = useState<T>(initial);
  const [errors, setErrors] = useState<Record<string, string | undefined>>({});

  const submit = () => {
    const validationErrors = validate(values);
    setErrors(validationErrors);
    if (Object.values(validationErrors).every((e) => !e)) {
      // submit success
    }
  };

  return { values, errors, setValues, submit };
}

// Передаем любую реализацию валидации извне:
const { submit } = useCustomForm(initialData, zodValidator(myZodSchema));
```

## 3. Liskov Substitution Principle (LSP)

> _Объекты/компоненты подтипов должны корректно заменять базовые сущности без нарушения ожидаемого поведения программы._

В React это означает: **компоненты-обертки должны сохранять контракт базового элемента** (пропсы HTML-элементов, `ref`, события).

### Пример 3.1: Корректное расширение нативных HTML-элементов

**Антипаттерн:** Кастомный `SearchInput`, который ломает нативные свойства (`onChange`, `disabled`, `ref`), принимая вместо них кастомный `onCustomChange`.

```tsx
// ❌ Нарушение LSP: нельзя подставить вместо стандартного <input />
export const SearchInput = ({
  onCustomChange,
  val,
}: {
  onCustomChange: (t: string) => void;
  val: string;
}) => <input value={val} onChange={(e) => onCustomChange(e.target.value)} />;
```

**Решение по LSP:**

```tsx
// ✅ Соблюдение контракта: компонент принимает ВСЕ валидные пропсы input + forwardRef
export interface SearchInputProps extends React.ComponentPropsWithRef<"input"> {
  searchIconPosition?: "left" | "right";
}

export const SearchInput = forwardRef<HTMLInputElement, SearchInputProps>(
  ({ searchIconPosition = "left", className, ...restProps }, ref) => {
    return (
      <div className="input-wrapper">
        {searchIconPosition === "left" && <IconSearch />}
        <input
          ref={ref}
          className={clsx("base-input", className)}
          {...restProps}
        />
      </div>
    );
  },
);
SearchInput.displayName = "SearchInput";
```

### Пример 3.2: Взаимозаменяемые провайдеры кэша / стейта

Если у вас есть абстракция над хранилищем (например, `StorageAdapter`), любая реализация (Local Storage, Session Storage, IndexedDB) должна возвращать совместимый интерфейс:

```tsx
export interface KeyValueStore {
  getItem: (key: string) => string | null;
  setItem: (key: string, value: string) => void;
}

export const LocalStoreAdapter: KeyValueStore = {
  getItem: (k) => localStorage.getItem(k),
  setItem: (k, v) => localStorage.setItem(k, v),
};

export const MemoryStoreAdapter: KeyValueStore = (() => {
  const map = new Map<string, string>();
  return {
    getItem: (k) => map.get(k) ?? null,
    setItem: (k, v) => map.set(k, v),
  };
})();

// Хук работает с ЛЮБЫМ адаптером без изменения логики
export const usePersistedState = (key: string, adapter: KeyValueStore) => {
  const [val, setVal] = useState(() => adapter.getItem(key));
  // ...
};
```

## 4. Interface Segregation Principle (ISP)

> _Клиенты не должны зависеть от интерфейсов и данных, которые они не используют._

В React: **не передавайте весь гигантский объект сущности (User, Product, Order) в компонент, которому нужны 1–2 поля.**

### Пример 4.1: Props Segregation в UI-компонентах

**Антипаттерн:** Передача 50-польной модели `User` в аватарку.

```tsx
// ❌ Нарушение ISP: аватарке нужен только url и имя, но она жестко связана со всей схемой User
export const UserAvatar = ({ user }: { user: FullUserModel }) => (
  <img src={user.profile.avatarUrl} alt={user.personalInfo.fullName} />
);
```

**Решение по ISP:**

```tsx
// ✅ Минимальный независимый интерфейс
interface AvatarProps {
  src?: string;
  alt: string;
  size?: 'sm' | 'md' | 'lg';
}

export const Avatar = ({ src, alt, size = 'md' }: AvatarProps) => (
  <img src={src || '/default.png'} alt={alt} className={`avatar-${size}`} />
);

// Теперь Avatar можно переиспользовать для User, Group, Bot, Product:
<Avatar src={user.avatarUrl} alt={user.name} />
<Avatar src={group.logo} alt={group.title} />
```

### Пример 4.2: Разделение интерфейсов Context

**Антипаттерн:** Единый контекст `AppContext`, в котором лежат тема оформления, сессия пользователя, корзина и методы роутинга. Изменение корзины триггерит ререндер компонентов, слушающих только тему.

```tsx
// ✅ Разделенные изолированные контексты
export const ThemeContext = createContext<{
  theme: "dark" | "light";
  toggleTheme: () => void;
} | null>(null);
export const UserSessionContext = createContext<{
  user: User | null;
  logout: () => void;
} | null>(null);

// Компонент подписывается строго на то, что ему нужно:
export const ThemeToggle = () => {
  const { theme, toggleTheme } = useTheme(); // Никак не реагирует на изменение user / session
  return <button onClick={toggleTheme}>{theme}</button>;
};
```

## 5. Dependency Inversion Principle (DIP)

> _Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба типа модулей должны зависеть от абстракций._

В React DIP реализуется через **React Context, передачу зависимостей через параметры хуков / пропсы и Service Locator / DI**.

### Пример 5.1: Инверсия механизма API-запросов через Context

**Антипаттерн:** Компонент напрямую импортирует экземпляр `axios` с жестко зашитым URL.

```tsx
// ❌ Жесткая связь с конкретным клиентом
import { globalAxiosInstance } from "@/services/axios";

export const UserProfile = ({ id }: { id: string }) => {
  useEffect(() => {
    globalAxiosInstance.get(`/users/${id}`); // Невозможно протестировать без мока глобального модуля
  }, [id]);
};
```

**Решение по DIP:**

```tsx
// 1. Абстракция (контракт)
export interface IUserService {
  getUser(id: string): Promise<User>;
}

// 2. Контекст как контейнер внедрения зависимостей
const ServiceContext = createContext<{ userService: IUserService } | null>(
  null,
);

export const useUserService = () => {
  const ctx = useContext(ServiceContext);
  if (!ctx) throw new Error("ServiceContext missing");
  return ctx.userService;
};

// 3. Компонент зависит от абстракции:
export const UserProfile = ({ id }: { id: string }) => {
  const userService = useUserService();
  const { data } = useQuery({
    queryKey: ["user", id],
    queryFn: () => userService.getUser(id),
  });
  return <div>{data?.name}</div>;
};

// В проде провайдим REST/Axios, в тестах/Storybook — InMemoryMockService:
<ServiceContext.Provider value={{ userService: new MockUserService() }}>
  <UserProfile id="1" />
</ServiceContext.Provider>;
```

### Пример 5.2: Инверсия стратегии валидации формы

```tsx
// Хук формы не знает, какая библиотека проверяет поля (Zod, Yup, чистый regex)
export type ValidatorFn<T> = (values: T) => Record<keyof T, string | undefined>;

export function useCustomForm<T extends Record<string, unknown>>(
  initial: T,
  validate: ValidatorFn<T>,
) {
  const [values, setValues] = useState<T>(initial);
  const [errors, setErrors] = useState<Record<string, string | undefined>>({});

  const submit = () => {
    const validationErrors = validate(values);
    setErrors(validationErrors);
    if (Object.values(validationErrors).every((e) => !e)) {
      // submit success
    }
  };

  return { values, errors, setValues, submit };
}

// Передаем любую реализацию валидации извне:
const { submit } = useCustomForm(initialData, zodValidator(myZodSchema));
```

## Сводная шпаргалка

| Принцип     | Вопрос для самопроверки в React                                                       | Ключевой инструмент                                             |
| ----------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **S** (SRP) | Занимается ли хук/компонент только одной задачей?                                     | Custom hooks, утилиты, UI-компоненты                            |
| **O** (OCP) | Могу ли я добавить новое поведение без правок исходного компонента?                   | `children`, Render Props, Compound Components                   |
| **L** (LSP) | Ломает ли мой кастомный компонент контракт нативного HTML-элемента или базового хука? | `forwardRef`, `ComponentPropsWithRef`, строгие типы интерфейсов |
| **I** (ISP) | Не передаю ли я лишние поля объекта в компонент, которому они не нужны?               | Деструктуризация, плоские (flat) пропсы, раздельные контексты   |
| **D** (DIP) | Не зашит ли внешний сервис (API, LocalStorage) намертво внутрь компонента?            | React Context, Render Props, DI через аргументы хуков           |
