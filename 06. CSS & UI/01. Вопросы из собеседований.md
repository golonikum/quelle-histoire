# ИИ

## minmax(0,1fr) для display: grid

Какое преимущество даёт использование `minmax(0,1fr)` вместо просто `1fr` в реальных макетах?

```css
.container {
  display: grid;
  grid-template-columns: repeat(3, minmax(0, 1fr));
}
```

**Ответ:**

Использование `minmax(0,1fr)` ограничивает минимальную ширину колонки нулём, что позволяет содержимому «сжиматься» внутри ячейки и не заставляет колонку расширяться из-за свойств типа `min-content` или длинных слов. Это особенно важно при вложенных flex-элементах, когда у них есть `min-width:auto` и они не хотят сжиматься меньше содержимого. Установка явного минимума в 0 говорит браузеру: колонку можно сжимать вплоть до нуля, если это нужно для соблюдения сетки. В результате сетка остаётся ровной, а переполнение контролируется с помощью overflow и других свойств, а не ломает всю компоновку.

## position: sticky

Для элемента:

```css
.header {
  position: sticky;
  top: 0;
}
```

Страница прокручивается, но .header не прилипает к верху. Какое из условий ЧАЩЕ всего является причиной такой проблемы?

**Ответ:**

Если один из родителей sticky-элемента имеет overflow отличное от `visible` (например, `hidden`, `auto` или `scroll`), область прокрутки для sticky ограничивается этим родителем. В результате, если именно этот контейнер не прокручивается (или его высота равна высоте содержимого), эффект прилипания не будет заметен: элемент либо не сдвигается, либо «отлипает» вместе с родителем. Это одна из наиболее частых причин, почему `position:sticky` «не работает» в реальной верстке. Для корректной работы нужно, чтобы цепочка родителей до скроллирующего контейнера не прерывалась блоком с `overflow`, который скрывает или ограничивает область прокрутки, иначе sticky-элемент будет «прилипать» лишь внутри этого локального контекста, а не относительно окна.

## transform: translateZ(0) или translate3d(0,0,0)

Есть элемент:

```css
.card {
  transform: translateZ(0);
}
```

Зачем иногда разработчики добавляют `translateZ(0)` или `translate3d(0,0,0)` к элементам?

**Ответ:**

Добавление трёхмерной трансформации вроде `translateZ(0)` или `translate3d(0,0,0)` может заставить браузер поместить элемент в отдельный композитный слой и использовать GPU для обработки анимаций и трансформаций. Это иногда сглаживает рывки и улучшает плавность, особенно при сложных движениях или эффектах, накладываемых на большой элемент. Однако этот приём нужно применять осторожно: избыточное количество слоёв может наоборот ухудшить производительность и увеличить потребление памяти. Для middle/senior-уровня важно понимать не только сам трюк, но и его стоимость: это не «волшебная кнопка» ускорения, а тонкий инструмент оптимизации, который следует использовать точечно и измерять результат с помощью профилировщиков браузера.

## У вас есть flex-контейнер с тремя элементами. Нужно, чтобы средний элемент занимал всё доступное оставшееся пространство, а крайние имели ширину по содержимому. Какой набор свойств подходит лучше всего?

**Ответ:**

```
Крайние: flex: 0 0 auto;, средний: flex: 1 1 auto;
```

Такой набор говорит flex-контейнеру: крайние элементы не растягивать (flex-grow: 0), не сжимать без необходимости (flex-shrink: 0) и оставлять им размер по содержимому (flex-basis: auto). Средний элемент, наоборот, может расти (flex-grow: 1) и сжиматься (flex-shrink: 1), занимая всё оставшееся место после того, как крайним будет выделена их естественная ширина. Это классический паттерн для построения макетов с «резиновой» центральной частью (например, центральный контент между левым и правым блоками). Такое решение ведёт себя предсказуемо при изменении ширины контейнера и корректно работает с переполнением, если для среднего элемента заданы дополнительные ограничения, такие как min-width или max-width.

## Какое утверждение верно для CSS Container Queries по сравнению с Media Queries?

**Ответ:**

Container Queries позволяют применять стили, исходя из размеров родительского контейнера, а не всего viewport.

Основное отличие Container Queries от Media Queries в том, что они ориентируются не на размеры viewport (окна браузера), а на размеры конкретного контейнера, помеченного как container (например, через container-type: inline-size;). Это позволяет строить по-настоящему компонентный, «контейнеро-ориентированный» дизайн, где карточка, виджет или блок может менять свою раскладку в зависимости от того, сколько места ему выделено в макете. Например, тот же компонент может выглядеть по-разному в узкой боковой колонке и в широком центральном столбце, даже если ширина экрана не меняется. Такой подход снимает жёсткую привязку к глобальным брейкпоинтам и делает дизайн более гибким и переиспользуемым.

## underline‑эффект

Есть список ссылок в навигации:

```xml
<nav>
  <a href="#" class="link">Главная</a>
  <a href="#" class="link">Каталог</a>
  <a href="#" class="link">Контакты</a>
</nav>
```

Нужно сделать плавный underline‑эффект при ховере, который «выезжает» слева направо, не сдвигая текст. Какой подход лучше всего подходит?

**Ответ:**

```
Использовать псевдо‑элемент ::after с position: absolute; transform: scaleX(...) и transform-origin: left
```

Псевдо‑элемент `::after`, абсолютно позиционированный относительно ссылки `(position: relative` у `.link`), позволяет нарисовать кастомную линию под текстом, не влияя на его размеры. Изначально можно задать ему `transform: scaleX(0)` и `transform-origin: left`, а при ховере/фокусе анимировать до `scaleX(1)` с помощью `transition`. Так текст остаётся на месте, а линия визуально «выезжает» слева направо. Этот приём хорошо контролируется, легко настраивается под дизайн и не ломает метрики строки.
